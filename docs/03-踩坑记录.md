# 03 — 踩坑记录

这里记录**失败的尝试**和**为什么失败**，避免后来者重复。

---

## 一、安装阶段

### 1.1 内核 panic：`please go to https://panic.apple.com to report this panic`

连续 4 次 panic，排查出两个诱因 + 一个真凶：

| 组件 | 问题 | 处理 |
|---|---|---|
| `IntelBTPatcher.kext` | 在 Tahoe 上崩溃蓝牙 | 禁用（后来配合 BlueToolFixup 才重新启用） |
| `RestrictEvents.kext` | 调用 Lilu `GetVariable` 崩溃 | 禁用 |
| **`OpenVariableRuntimeDxe.efi`** | **真凶** | **永久禁用** |

**真凶的机理**：

`OpenVariableRuntimeDxe.efi`（模拟 NVRAM）提供的假 `GetVariable`，
在 `ExitBootServices` 之后其运行时代码页变成 NX（不可执行），于是：

```
Kernel trap type=14 (page fault)
CR2 == RIP          ← 取指故障，跳到了不可执行的页
```

**这是 AMD 平台上最常见的 panic 原因之一。GEM12 必须永久禁用这个驱动。**

### 1.2 卡在 `CoreAnalyticsHub start completed`

**原因**：`SSDT-PLUG-ALT.aml` 被禁用。
AMD 的 CPU 拓扑必须由这个 SSDT 提供，否则内核在初始化 CPU 电源管理时挂起。

**修复**：启用 `SSDT-PLUG-ALT.aml`。

### 1.3 卡在 `Initializing XNU platform expert`

**原因**：EFI 里混入了笔记本专用组件：

- `SSDT-PNLF.aml`（内屏背光）
- `SSDT-ALS0.aml`（环境光传感器）
- `SSDT-XOSI.aml`（Windows 兼容层）
- `SMCBatteryManager.kext`（电池）
- `SMCLightSensor.kext`
- `BrightnessKeys.kext`

GEM12 是迷你主机，没有这些硬件。

**修复**：全部移除。

### 1.4 `OC: Driver apfs_aligned.efi at 0 cannot be found! Halting on critical error`

**原因**：往 EFI 分区写 17 GB 安装包时把 EFI 分区写坏了。

**修复**：从备份重建 EFI。

**教训**：安装包绝不能放在 EFI 分区（只有 200 MB）。

## 二、离线安装阶段

### 2.1 `installer -pkg` 在恢复环境失败

```
The install failed. (运行软件包"InstallAssistant.pkg"的脚本时出错。)
```

日志：

```
./postinstall.sh: cp: .../Install macOS 27 Golden Gate.app/Contents/SharedSupport/SharedSupport.dmg:
fcopyfile failed: No space left on device
```

**原因**：macOS Recovery 是精简系统，`installer` 的 postinstall 脚本依赖
PackageKit 等组件，在 Recovery 里跑不完整。

**最终方案**：用 `xar` 直接解包 + `startosinstall`，绕过 PackageKit。

### 2.2 `xar -xf` 后 `Payload` 解不开

`Payload` 只有 14 MB，`bsdtar` 报 `Unrecognized archive format`。

**发现**：`InstallAssistant.pkg` 的结构是

```
Payload            14 MB    ← Install macOS.app 骨架
SharedSupport.dmg  17.1 GB  ← 真正的系统镜像
```

而 `postinstall.sh` 做的事情就是把 dmg 复制进 app 的 `Contents/SharedSupport/`。

**教训**：`Payload` 14 MB 是正常的，不是损坏。

### 2.3 APFS 卷名是 `" OC"`（带前导空格）

硬编码 `/Volumes/OC` 失败。必须自动探测：

```sh
for v in /Volumes/*; do
  ft=$(mount | grep -F " on $v " | sed -n 's/.*(\([a-z0-9]*\),.*/\1/p')
  case "$ft" in apfs|hfs) T="$v" ;; esac
done
```

### 2.4 Recovery 环境缺失的工具

| 工具 | 状态 |
|---|---|
| `xar` | ✅ |
| `bsdtar` | ✅ |
| `ditto` | ✅ |
| `installer` | ⚠️ 存在但脚本跑不了 |
| `diskutil` / `mount` / `df` | ✅ |
| `pkgutil` | ❌ |
| `ssh-keygen` | ❌ |
| `passwd` | ❌ |
| `df -T` | ❌ |
| `python3` | ❌ |

**`df -T` 不可用**，判断文件系统要用：

```sh
mount | grep -F " on $v " | sed -n 's/.*(\([a-z0-9]*\),.*/\1/p'
```

## 三、网络阶段

### 3.1 板载 Intel I226-V：四个方案，全部失败

`8086:125C`，双 2.5G 口。这个问题**花了整整两轮排查**，最后结论是：
**这块网卡在 macOS 上目前没有可用的驱动方案。**

四个方案依次试过，每一层的症状都不一样：

| 方案 | 链路 | RX | 结果 |
|---|---|---|---|
| 原生 `AppleEthernetE1000` | ❌ | — | PHY 协商不出链路 |
| `AppleIGC` v1.9 | ✅ | ❌ | RX 完全死（MSI bug） |
| `AppleIGC` v1.8 | ✅ | ✅ | `M_PKTHDR` 内核 panic |
| `AppleIGC` 自编译（v1.9 + 补丁） | — | — | 两个编译坑导致从未加载 |

下面按实际排查顺序记录，因为这中间有**五层完全不同的故障**，
症状都是"没网"，很容易混为一谈。

---

#### 第一层：原生 `AppleEthernetE1000` —— 驱动绑定成功，但没有链路

装完系统进桌面后一切看起来都对：

```sh
system_profiler SPEthernetDataType
#   Intel(R) I226 V:
#     Driver: com.apple.DriverKit-AppleEthernetE1000
#     BSD Device Name: en0
#     MAC Address: c8:ff:bf:03:d1:5c

ioreg -rc IOUserNetworkEthernet -d1
#   +-o DriverKit_AppleEthernetE1000
#         <class IOUserNetworkEthernet, registered, matched, active>
#         "IOModel" = "Intel(R) I226 V"
#         "IOPowerManagement" = {"CurrentPowerState"=3, "MaxPowerState"=3}
```

驱动实例 `registered, matched, active`，MAC 读得到，电源状态到 3 —— **驱动是好的**。

甚至 `networksetup -listValidMedia en0` 能列出完整的速率表：

```
10baseT/UTP ... 100baseTX ... 1000baseT ... 2500Base-T   ← 全部支持
```

**但**：

```sh
ifconfig en0
#   media: autoselect (none)     ← 没有链路
#   status: inactive
```

**验证过不是物理问题**：

| 验证 | 结果 |
|---|---|
| 网口 link 灯 | 亮；拔掉网线会灭 → **确认是 link 灯，物理层是通的** |
| 换另一个 RJ45 口 | 同样 `inactive` |
| 同一根线接 USB 网卡 | 正常上网 → **线和对端都是好的** |
| 强制 `1000baseT full-duplex` | 仍是 `(none)` |
| `ifconfig down/up` | 无效 |
| `pkill -f DriverKit-AppleEthernetE1000`（让驱动重新初始化） | 新进程起来后仍 `inactive` |
| `netstat -I en0` | `Ipkts=0`，`Opkts` 有几包 → 只发不收 |

**结论：macOS 自带的 DriverKit 驱动在这个平台 + I226-V 的组合上，
PHY 链路协商不成功。** 这不是配置问题，换 BIOS 设置也没用。

> 注：社区里确实有人说 I226-V 在 Tahoe 上"免驱直接用"。那在 Intel 主板上成立，
> 在 AMD 平台上不一定。**不要因为别人能用就认为自己的配置错了。**

---

#### 第二层：`AppleIGC.kext` —— 链路有了，但 RX 完全死掉

换成社区驱动 [SongXiaoXi/AppleIGC](https://github.com/SongXiaoXi/AppleIGC) 后：

```sh
ifconfig en0
#   media: autoselect (2500Base-T <full-duplex,flow-control>)   ← 链路建立了！
#   status: active
```

**链路问题解决了。** 而且不需要加 `e1000=0`：

`AppleIGC` 的 `IOProbeScore = 4000`，高于原生 dext 的 `3000`，
所以它会**自动抢占**，原生驱动自然让位。

**但网络还是不通** —— 卡在 `169.254.22.196`（APIPA 自动私网地址）：

```sh
netstat -I en0 -b
#   Name  Mtu  Network  Address         Ipkts Ierrs  Ibytes  Opkts Oerrs  Obytes
#   en0   1500 169.254  gaodemacbook-pr     0     0       0      -      -   28980
#                                          ↑                  ↑
#                                     收包永远是 0        发包在涨
```

用 `tcpdump` 抓 12 秒，**一个包都没有**（正常局域网至少几百个 ARP/广播包）：

```sh
sudo tcpdump -i en0 -n
#   0 packets captured
#   0 packets received by filter
```

路由器那边能看到 DHCP 请求并尝试分配 IP（`192.168.1.128`），
但 offer 回不来 —— **典型的 TX 通、RX 死**。

---

#### 第三层：根因 —— `AppleIGC` v1.9 的 MSI 中断 bug

翻到 upstream 的 [issue #40](https://github.com/SongXiaoXi/AppleIGC/issues/40)，
症状逐条对得上（`IOLinkStatus=3`、`IOLinkSpeed=2500000000`、`Ipkts=0` 但 `Obytes` 增长、
DHCP 掉 169.254、ping 100% 丢包）。

作者已经把源码定位到行：

```c
// AppleIGC.cpp  pci_enable_msi_block()
static int pci_enable_msi_block(IOPCIDevice *dev) {
    int status = -EINVAL, maxvec;        // ← 初始化为错误码
    if (dev->findPCICapability(kIOPCIMSICapability, &pos) == 0)
        return -EINVAL;
    ...
#if 0
    status = pci_msi_check_device(...);      // 被禁用了
#endif
#if 0
    status = msi_capability_init(dev, nvec); // 真正的 MSI 设置也被禁用了
#endif
    return status;                           // 永远返回 -EINVAL
}
```

于是：

```c
if (!pci_enable_msi_block(adapter->pdev))
    adapter->flags |= IGC_FLAG_HAS_MSI;   // 永远不执行 → MSI 从未在硬件上启用
```

**但 v1.9 的 PR #38 仍然让驱动去监听 MSI 中断源**：

```c
for (int index = 0; ; index++) {
    provider->getInterruptType(index, &interruptType);
    if (interruptType & kIOInterruptTypePCIMessaged) {
        interruptIndex = index;      /* → 1 */
        usingMsi = true;
        break;
    }
}
```

结果：**驱动监听一个从未启用的 MSI 向量 → 中断永不触发 →
`interruptOccurred()` 永不调用 → RX 永不处理**。

TX 不受影响，因为它是同步路径，不需要中断。这正好解释了"只发不收"。

issue 里作者实测：MSI 源在时 `IrqCount = 0`；
强制用 legacy INTx（`interruptIndex = 0; usingMsi = false;`）后
`IrqCount = 46528`，`ICR = 0x80000080`（`INT_ASSERTED | RXT0`），DHCP 立刻成功。

---

#### 第四层：降到 `AppleIGC` **v1.8** —— RX 通了，但会 panic

`PR #38`（`1e89a6c Fix I225-V stalls by selecting PCI MSI interrupt source`）
是 **v1.9 才加入**的。对比 `v1.8...v1.9` 的 commit 列表可以确认：

```
13946f4  chore: bump version to 1.9 and replace TX cursor method
7affffc  fix: enable manual media selection
0a98017  Merge pull request #37
1e89a6c  Fix I225-V stalls by selecting PCI MSI interrupt source (#38)   ← 问题来源
8802cba  fix: implement frame discarding mechanism in RX ring
```

**v1.8 没有这段 MSI 选择逻辑，用的是 legacy INTx，RX 正常。**

降级后实测（这部分是成功的）：

```sh
ifconfig en0
#   inet 192.168.1.128 netmask 0xffffff00     ← DHCP 成功
#   media: autoselect (2500Base-T <full-duplex,flow-control>)
#   status: active

netstat -I en0 -b
#   Ipkts=7472   Ibytes=4680524     ← RX 活了
#   Opkts=4052   Obytes=872594

ping -c 3 192.168.1.1
#   3 packets transmitted, 3 packets received, 0.0% packet loss
#   round-trip min/avg/max = 0.396/0.498/0.573 ms     ← 2.5G 有线，0.5ms

curl --interface 192.168.1.128 https://www.apple.com
#   HTTP 200
```

**但随后出现内核 panic —— 而且是在做很普通的操作时触发的：**

| 时间 | 用户操作 | panic |
|---|---|---|
| 04:38 | 点控制中心的「镜像」按钮 | `m->m_flags & M_PKTHDR` |
| 04:42 | 点「音量」滑块 | `m->m_flags & M_PKTHDR` |

```
panic(cpu 0): assertion failed: m->m_flags & M_PKTHDR,
  uipc_mbuf.c:4839 @uipc_socket.c:8286
Backtrace: _dlil_create_input_thread + 0x2257 / +0x2596
Panicked task: pid 0: kernel_task
```

**症状分析**：`_dlil_create_input_thread` 是网络输入线程，
`M_PKTHDR` 是 mbuf 的「包头」标志位。这个断言失败意味着
**驱动交给协议栈的 mbuf 缺少 `M_PKTHDR`**，内核在 socket 层直接 panic。

点按钮只是恰好触发了网络活动（iCloud 同步、App Store 检查），
**不是按钮本身的问题**。

> 注意：源码里 `AppleIGC::receive()` 确实有 `M_PKTHDR` 检查并会丢弃坏包，
> 说明这个防护存在但没覆盖所有路径（或者 mbuf 在后续环节被改坏）。

---

#### 第五层：自己编译 v1.9 + 补丁 —— 结果全程没加载成功过

既然 v1.9 只差 MSI 那一个 bug，那就**自己编译 v1.9 并打上 issue #40 的补丁**：

```c
// initEventSources() 里，把「找第一个 MSI 源」改成固定用 legacy INTx
provider->getInterruptType(0, &interruptType);
interruptIndex = 0;
usingMsi = false;
```

顺带还修了一个移植 bug：macOS 移植版没有 Linux 的 page frag 机制，
`igc_add_rx_frag()` 用 `mbuf_copyback()` 复制**整个帧**，
但分配时只给了 `IGC_RX_HDR_LEN`（256 字节）——
1500 字节的帧会被拆成 6~7 个 mbuf 的链。改成按 `IGC_RXBUFFER_2048` 分配。

编译方法见 [patches/AppleIGC-源码修改.md](../patches/AppleIGC-源码修改.md)
（本机只有 Command Line Tools，`xcodebuild` 不可用，要手工调 `clang` + `ld -kext`）。

**然后踩了两个坑，导致前两版编译产物根本没被加载：**

| 坑 | 后果 |
|---|---|
| `CFBundleVersion` 写成 `1.9-gem12c`（带字母） | 内核报 `bad value`，**静默拒绝加载** |
| 手工 `ld -kext` 没有 `_kmod_info` 符号 | 内核无法登记 kext，加载失败 |

第一条的内核日志只有一行，很容易漏掉：

```
Kext com.sxx.AppleIGC error - CFBundleVersion bad value '1.9-gem12c'.
```

第二条要靠对比符号表才能发现（官方 143 个导出符号 vs 我们 142 个，差的正是 `_kmod_info`）。

**所以在很长一段时间里，我们都在跟一个"从未加载的驱动"较劲。**
期间出现的 `pmap` 内存损坏 panic——

```
panic(cpu 13): Possible memory corruption:
pmap_pv_remove(...): null pv_list, priors: 2 @pmap_internal.h:893
Panicked task: pid 571: FamilyControlsAgent
```

—— 其实与 AppleIGC 无关，是 `nullarc` 的 GPU 接管造成的
（详见 [07-稳定性与崩溃分析.md](07-稳定性与崩溃分析.md)）。

等两个坑都填掉之后，kext 终于能被识别，但加载被系统拒绝：

```
Extension with identifiers com.sxx.AppleIGC not approved to load.
  Please approve using System Settings.
```

**最终结论：这个方案不可用。**

> **重要教训**：改完 `config.plist` 里的 `Enabled = true` **不等于 kext 生效了**。
> 每次都要确认：
> ```sh
> kmutil showloaded | grep -i igc
> ioreg -rc AppleIGC -d1
> ```
> kext 加载失败通常是**静默的**。

---

#### 结论：这块 I226-V 在 macOS 上目前没有可用驱动

| 方案 | 结果 |
|---|---|
| **原生 `AppleEthernetE1000`** | ❌ 驱动能绑定、MAC 能读、速率能力完整，但 **PHY 协商不出链路** |
| **AppleIGC v1.9** | ❌ link 正常，但 **RX 完全死**（MSI 从未启用） |
| **AppleIGC v1.8** | ❌ RX 能用，但 **`M_PKTHDR` 内核 panic** |
| **AppleIGC v1.9-gem12（自编译）** | ❌ 两个编译坑导致**从未加载**；修好后被系统拒绝加载 |

**推荐替代**：

1. **Wi-Fi**（Intel AX210，`AirportItlwm` 2.4.0）—— 当前生产方案
2. **USB 网卡 AX88179B** —— `com.apple.driver.usb.cdc.ncm` 原生驱动，免驱即插即用

本仓库的 `efi/EFI/OC/config.plist` 里 `AppleIGC` **默认 `Enabled = false`**，
但 kext 文件和 [patches/AppleIGC-源码修改.md](../patches/AppleIGC-源码修改.md)
都保留了（含补丁、编译方法、四个坑），方便以后跟进上游修复。
---

#### 快速判断"网卡到底哪一层坏了"

按这个顺序，每步都能排除一层：

```sh
# 1. 驱动有没有绑定？（看 registered, matched, active）
ioreg -rc IOUserNetworkEthernet -d1 | grep -E 'IOModel|IOInterfaceName'

# 2. 有没有链路？（autoselect (none) = 物理层没协商上）
ifconfig en0 | grep -E 'status|media'

# 3. 能不能收包？（Ipkts 是不是一直是 0）
netstat -I en0 -b | tail -1

# 4. 接口上到底有没有流量？（0 packets = RX 死的铁证）
sudo tcpdump -i en0 -n

# 5. DHCP 有没有响应？
sudo ipconfig getpacket en0
```

| 症状 | 位置 |
|---|---|
| 没有 `IOUserNetworkEthernet` 节点 | 驱动没加载 → 检查 `Kernel → Add` / `MinKernel` |
| `media: autoselect (none)` | PHY 没协商 → **换驱动**（本例） |
| `Ipkts` 恒为 0 但 `Obytes` 增长 | **RX 中断问题**（本例 v1.9 bug） |
| `Ipkts` 有值但 DHCP 失败 | 上层问题 → 查路由器 / 网络服务顺序 |

> **`Ipkts=0` + `Obytes` 增长 = 中断问题**，这是本项目最值钱的一条经验。

#### 回退方法

```sh
# 备份位置（本机）
ls /Users/Shared/gpu/backup/AppleIGC-v1.8.kext     # 原始 v1.8（RX 通但 panic）
ls /Users/Shared/gpu/backup/AppleIGC-v1.9.kext     # 原始 v1.9（RX 死）
ls /Users/Shared/gpu/backup/EFI.before-igc.*       # 装 AppleIGC 之前的完整 EFI

# 彻底关掉 AppleIGC（默认配置就是这样）：
# config.plist → Kernel → Add → AppleIGC.kext → Enabled = false
```

#### 顺带一提

- **如果哪天 AppleIGC 能用**，有线接管后 Wi-Fi 会自动掉线（`en3` 变 `inactive`），
  这是正常的：网络服务顺序里 `Ethernet` 优先，系统会切到有线。
- 想改主用网卡：`系统设置 → 网络 → 右下角「…」→ 设定服务顺序`
- **现在这台机器的主用网络是 Wi-Fi**，IP 会随随机 MAC 变化，
  SSH 前先用路由器看 DHCP 租约。



### 3.2 USB 网卡 AX88179（老款）在 Recovery 里 0 B/s

```
en2: media: autoselect (1000baseT)
     status: active
ping 网关: 3048/3572/4096 ms
下载速度: 0 B/s
首字节:   14.3 秒
```

**根因**：AX88179（PID `0x1790`）在 macOS 下**需要 ASIX 专用 DEXT 驱动**，
而 Recovery 环境没有。能 DHCP、能 ping（小包），但大流量走不动。

**对比**：

| 芯片 | macOS 原生支持 |
|---|---|
| **AX88179**（老款） | ❌ 需专用 kext |
| **AX88179A / AX88179B** | ✅ CDC-NCM 原生 |
| **RTL8153 / 8153B** | ✅ `AppleUSBRealtek8153` |
| RTL8156（2.5G） | ⚠️ 有问题 |

**最终用的网卡**：AX88179B（`0B95:1790` 的 B 版），USB 5 Gbps 枚举，正常工作。

### 3.3 曾怀疑是 USB4 口的问题

GEM12 有 USB4（`1022:1668` / `1669`），而 macOS 对 AMD USB4 零支持。

但实测换成 USB-A 口后依然 0 B/s，**排除了这个假设**——
真正原因是 AX88179 老款缺驱动。

## 四、GPU 阶段（最长的部分）

详细的逐层排查见 [01-GPU接管.md](01-GPU接管.md)，这里只列失败的分支。

### 4.1 `hdmi-fb2` 分支不可用

`izerok/nullarc` 的 `hdmi-fb2` 分支走的是「head 1 + `phxfb1_config` 手动配置」路线。

尝试结果：

- `PhxAMDFB on the panel: 1` 能触发
- timing 查询正常
- `MM commit MAPPED` 成功
- **WindowServer 依然在 CoreDisplay 断言**

**结论**：这条路线未经验证，放弃。

### 4.2 `phxfb_hdmi=1`（PhxHDMIHead）会卡死

main 分支（`3497d87`）里有个 `PhxHDMIHead` 类，
设计意图是给「无内建屏、只有外接」的机器提供一个假显示器（内置 1080p EDID）。

在 `phxboot.sh` 的 M2 分支里加：

```sh
sysctl -w debug.phxfb_hdmi=1
```

**结果：系统直接卡死。**

```
23:31:20  phxboot
PhxAMDFB on the panel: 1
（之后没有任何日志，连 compute 测试都没跑）

23:37:18  phxboot
previous attempt did not finish: phxboot and PhxAMDFB off
PhxAMDFB took the panel: rebooting
```

**原因**：`PhxHDMIHead::start()` 要配置 DCN 硬件去扫描
`fBase + 0x01000000`，但那个位置没有真实的 framebuffer，硬件配置卡住。

**这个功能是未文档化的实验代码，K8 项目也没用它。**

**已回滚。**

### 4.3 `reduceTransparency` 对帧率的影响

现象：GPU 合成能工作，但拖动窗口只有 2 fps，WindowServer CPU 197%。

`sample` 抓到的栈：

```
CompositorMetal::CompositeLayersToDestination
  → CompositorMetal::composite
    → MetalCompositeLayer
      → CARenderOGLRenderDisplayWithOptions
        → CA::OGL::render
          → CA::OGL::render_layers        ← 递归开始
            → CA::OGL::LayerNode::apply
              → CA::OGL::render_layers    ← 递归
                ...（10+ 层）
```

**原因**：毛玻璃（backdrop blur）导致的图层递归渲染。

**修复**：

```sh
defaults write com.apple.universalaccess reduceTransparency -bool true
defaults write com.apple.universalaccess reduceMotion -bool true
```

**效果**：2 fps → 57 fps。

**代价**：界面失去毛玻璃效果。且这两个设置在重启后会被重置
（写入的是 root 域而非用户域），需要重新设置。

### 4.4 误改壁纸导致的"背景黑"假象

测试时用了：

```sh
osascript -e 'tell application "System Events" to tell every desktop to set picture to "/System/Library/Desktop Pictures/Solid Colors/Black.png"'
```

后来排查"背景是黑的"，一度怀疑是 GPU 合成没渲染壁纸图层，
最后发现就是壁纸被设成了纯黑图。

**教训**：测试 UI 时改的壁纸，记得改回来。

## 五、容易踩的坑（总结）

| 坑 | 后果 | 规避 |
|---|---|---|
| `OpenVariableRuntimeDxe.efi` 启用 | **内核 panic（trap 14）** | 永久禁用 |
| 缺 `SSDT-PLUG-ALT.aml` | 卡在 `CoreAnalyticsHub` | 必须启用 |
| 混入笔记本专用 SSDT/kext | 卡在 `XNU platform expert` | 全部移除 |
| 安装包放 EFI 分区 | EFI 被写坏 | 放其它分区 |
| 硬编码 `/Volumes/OC` | 找不到卷（实际是 `" OC"`） | 自动探测 |
| 用 `df -T` | Recovery 里不支持 | 解析 `mount` 输出 |
| **在 Recovery 里看不到板载 I226-V** | **误判「无驱动」，多买一个 USB 网卡** | **装好系统后免驱，见 3.1** |
| 老款 AX88179 | Recovery 里 0 B/s | 用 B 版或 RTL8153 |
| 用官方 nullarc release | WindowServer 崩溃 | 用 `3497d87` + K8 补丁 |
| `phxfb_hdmi=1` | 系统卡死 | 不要用 |
| **`PhxGPU` 权限 700** | **显示器 offline** | **chmod 755** |
| 忘记 `phxboot-m2` | `PhxAMDFB` 不接管 | 创建标记文件 |
| `kHiTotal` 与 `kPoolTry` 不匹配 | VRAM 池只有 512 MB | 两边一起改 |

## 六、方法论：别把「环境限制」当成「硬件不支持」

这次的 3.1 是个典型例子，值得单独记一笔。

**错误推理链**：

```
Recovery 里 system_profiler 看不到 I226-V
  → 得出结论「macOS 没有 I226-V 驱动」
  → 买 USB 网卡替代
  → 文档里写上「板载网卡无驱动」
```

**错在哪**：把**一个精简环境**的观测结果，推广成了**整个系统**的能力判断。

**正确的验证姿势**：

| 想知道的 | 该在哪测 | 不该拿哪的结果下结论 |
|---|---|---|
| 硬件是否被系统支持 | **装好的完整系统** | Recovery / 安装器 |
| kext 是否加载 | `kextstat` / `ioreg` | `system_profiler`（它可能只是没显示） |
| 驱动是否绑定 | `ioreg -rc <驱动类>` 看 `registered, matched, active` | 看接口有没有 IP |
| 链路是否通 | `ifconfig` 看 `status` / `media` | 看能不能上网 |

**一句话**：`status: inactive` ≠ 驱动不存在，
`system_profiler` 没列出来 ≠ 系统不支持。
**先看 `ioreg` 里驱动类的绑定状态，再判断。**
