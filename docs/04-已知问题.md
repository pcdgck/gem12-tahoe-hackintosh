# 04 — 已知问题

以下都是**目前无解**或**未验证**的项目，不要浪费时间重复尝试。

---

## 一、完全不可用

### 1.1 音频（AMD ACP）

```
PCI 1022:15e3   AMD Audio Co-Processor
```

macOS 没有 AMD ACP 的音频驱动。Tahoe 26 还移除了 `AppleHDA.kext`，
所以连传统 HDA 路径都没了。

当前状态：

```
system_profiler SPAudioDataType
Audio:
    Devices:
（空）
```

`IOAudioEngine` 实例数 = 0。

**替代方案**：

1. **USB 声卡**（最省事，几十元）
2. **HDMI 音频**（如果显示器的 HDMI 支持音频回传）
3. **蓝牙耳机/音箱**（AX210 蓝牙已可用）

**不要尝试**：

- `AppleALC` + `alcid=xx` —— 对 ACP 无效
- `VoodooHDA` —— 对 ACP 无效
- 修改 `DeviceProperties` 注入 layout-id —— 没有 codec 可配

### 1.2 截屏 / 录屏

```sh
screencapture -x /tmp/test.png
→ could not create image from display
```

**原因**：nullarc 的读回（readback）路径未实现完整。

K8 文档提到 `phxbringup-ptfix`（页表 + VRAM 池扩容）能修好截屏，
但本项目已经应用了 ptfix 参数，截屏**依然失败**。

**可能原因**：K8 用的是 `hdmi-fb2` 之后的某个特定 commit，
或还有其它未公开的修改。

**影响**：无法截图、无法录屏、无法屏幕共享。

### 1.3 AirDrop / Handoff / 接力

**原因**：Intel 网卡无 AWDL（Apple Wireless Direct Link）。

```sh
ifconfig | grep awdl
（无输出）
```

`AirportItlwm` 明确不支持 AWDL。

**替代**：LocalSend / PairDrop 等局域网传文件工具。

### 1.4 USB-C 视频输出

```
USB4 NHI  1022:1668
USB4 NHI  1022:1669
```

`AppleThunderboltNHI` 没有 x86_64 可执行文件，且只匹配 Intel 的 device ID。

**所以 USB-C 口无法输出视频，也不能当扩展坞。**

**唯一路线**：USB DisplayLink 适配器（驱动 17.1 支持 Intel + Tahoe 26）。

### 1.5 WPA3-only Wi-Fi

`AirportItlwm` 只支持 WPA2-Personal 和 WPA2/WPA3 transition（含可选 PMF）。

**不支持**：

- WPA3-only（SAE）
- 强制 PMF

**规避**：路由器改成 WPA2 或混合模式。

## 二、部分可用

### 2.1 桌面合成 CPU 偏高

| 场景 | CPU |
|---|---|
| 空闲 | 0.2% |
| 打开窗口 | 4-9% |
| **拖动窗口** | **127%** |

**原因**：nullarc 架构的固有代价：

1. CA 图层准备 + Metal 绘制（CPU 侧）
2. `NVMTL_WS_WAIT_COMPLETION=1` 的忙等
3. 非 256B 对齐 surface 的每帧私有图像拷贝

**缓解**：

```sh
defaults write com.apple.universalaccess reduceTransparency -bool true
defaults write com.apple.universalaccess reduceMotion -bool true
```

去掉毛玻璃后帧率从 2 fps 提到 57 fps。
但 CPU 在拖动时仍会到 127%（K8 同代硬件也有类似现象）。

**这是上游架构问题，无法在本项目层面解决。**

### 2.2 无 HiDPI

`PhxAMDFB` 只报告固件 GOP 的单一模式（2160×1440），
没有提供 HiDPI 缩放模式。

**影响**：文字偏小、锐度一般。

### 2.3 只有单 HDMI 输出

受限于 1.4（USB-C 无视频），目前只有 HDMI 一个输出。

### 2.4 设置页 / 墙纸面板卡顿

**原因**（K8 文档的分析）：

1. WindowServer 冷启动后首次全量 SPIR-V 翻译（一次性，之后 memo 缓存）
2. `SCHEDULE_AFTER_SURFACE_WRITES=1` 的防花屏代价
3. 非 256B 对齐 surface 的每帧私有图像拷贝（墙纸 tab 缩略图多）

**这是 nullarc 架构的已知项，上游未修。**

### 2.5 睡眠 / 唤醒

**未充分验证。**

已知：带 `RyzenHV` 虚拟机时唤醒未测。
基础睡眠能否正常唤醒需要实际测试。

**如果出问题**，可以临时禁用：

```sh
sudo pmset -a sleep 0
```

### 2.6 动态壁纸导致 `VTDecoderXPCService` 长期占 90%+ CPU ★

**现象**：开机后 `VTDecoderXPCService` 持续 90%+ CPU、4 GB 内存，从不停止。

```
PID   COMMAND          %CPU  MEM
705   VTDecoderXPCServ 93.2  4.1 GB
194   WindowServer     28.8  548 MB
```

**原因链**：

1. Tahoe 的系统壁纸 `Tahoe Day` 是 **170 MB 的 HEVC `.mov`**
   （`/System/Library/Desktop Pictures/.wallpapers/Tahoe Day/Tahoe Day.mov`）
2. 780M 在 macOS 下**没有 VCN 硬件解码器**（`ioreg` 里 `IOVideoDevice` 计数为 0）
3. VideoToolbox 回落到**纯 CPU 软解**（加载 `VCPHEVC.bundle`）
4. `WallpaperAerialsExtension` 循环喂帧 → 解码器 24 小时不停

**关键：把桌面壁纸换成静态图没用。**
`WallpaperAerialsExtension` 服务的是**「空闲/锁屏」壁纸**（`Idle`），
和 `Desktop` 是两套独立配置。

```sh
plutil -p ~/Library/Application\ Support/com.apple.wallpaper/Store/Index.plist
# "Desktop" => Provider = com.apple.wallpaper.choice.image   ← 已经是静态
# "Idle"    => Provider = default                            ← 还是动态壁纸
```

**实测效果**（杀掉后）：

| 指标 | 之前 | 之后 |
|---|---|---|
| `VTDecoderXPCService` | 93.2% / 4.1 GB | 退出 |
| `WindowServer` | 28.8% | **9.8%** |
| load average | 4.66 | **3.14** |

**处理**：

```sh
# 手动杀一次，能管一段时间
sudo killall WallpaperAerialsExtension

# 或用现成看门狗（连续 3 次超 50% 才动手）
sudo cp scripts/vtdec-guard.sh /usr/local/bin/
sudo cp scripts/local.vtdecguard.plist /Library/LaunchDaemons/
sudo launchctl load -w /Library/LaunchDaemons/local.vtdecguard.plist
```

**更彻底**（需图形界面）：系统设置 → 墙纸 → 把**「锁屏」**那项也改成静态图片。

**试过但无效的方法**：

| 方法 | 结果 |
|---|---|
| `pluginkit -e ignore` | 系统扩展不受管，照样启动 |
| 删除 `Tahoe Day.mov` | `Read-only file system`（SSV 封印卷） |
| `killall WallpaperAgent` | 会把 Aerial 扩展一起拉起，更快复现 |

### 2.7 蓝牙搜不到设备 —— **射频信号极弱（天线）** ★

**现象**：控制器状态完全正常，但扫描一个设备都发现不了。

```
Address: EC:4C:8C:F2:F1:AB    State: On
Firmware: v8641 c8641          Transport: USB
deviceInquiryComplete: error:0 aborted:0 devicesFound:0
```

**逐层排除**（每一层都是好的）：

| 检查项 | 结果 |
|---|---|
| USB 枚举 | `8087:0x0029`，class 224，供电正常 |
| 固件加载 | `v8641 c8641` |
| HCI 通信 | 71 条命令正常收发 |
| 扫描启动 | `Scanning started successfully` |
| **实际收到的 BLE 广播** | **13 条** —— 射频**能收到数据** |
| **这些广播的 RSSI** | **-90 ~ -106 dBm** |

**关键证据**（能抓到手机的广播，但信号极弱）：

```
Identities resolve added: ... DsTy <NearbyInfoV2>, RSSI -100, Ch 37 ...
```

正常应在 **-40 ~ -70**。衰减 30-50 dB = **天线/射频物理连接问题**。

> ⚠️ 日志里的 `rssi -45` / `rssi -50` 是**扫描过滤阈值**，不是实际信号。
> 真正的信号强度看 `RSSI -xxx` 的广播记录。

**需要检查**（AX210 是 M.2 2230 卡，天线走两个 IPEX4 小接头）：

1. 机箱外天线（若有外置 SMA）是否拧紧
2. AX210 上的两个 IPEX4 接头是否扣到位（**轻轻按压，别扯断线**）
3. 两根天线是否都在 —— 只接一根时 Wi-Fi 勉强能用，蓝牙会残废
4. 走线有没有被螺丝/散热器压伤

**验证方法**：手机贴着机箱天线位置，再看 RSSI。

```sh
sudo log show --last 2m --predicate 'subsystem == "com.apple.bluetooth"' \
  | grep -oE 'RSSI -[0-9]+' | sort -u
```

- 贴近能到 **-60 左右** → 天线通了
- 贴近仍是 **-100** → 天线断了 / 没接

**软件侧已做到最好**（不是软件问题）：

`IntelBluetoothFirmware` 从 2.5.1 升到 **2.5.3**。2.5.2 加入了
`LE Data Length Change` 注入，清掉 `LE_READY_WAIT_FOR_LENGTH` stall ——
没有它，Tahoe 上 BLE 设备根本无法被发现。

> **`bluetoothd` 偶发崩溃是正常现象**：`BlueToolFixup` 必须在内存里
> patch `bluetoothd` 才能让第三方蓝牙工作，这会破坏代码页签名，
> Tahoe 的签名检查就会 `SIGKILL` 它。`launchd` 会立刻重启，表现是瞬断后自动恢复。
> `BlueToolFixup 2.7.2` 已是最新版，无法避免。

### 2.8 开启 GPU 接管后，Safari 及大批系统进程被 SIGKILL ★★★

**这是本项目最严重的可用性问题。** 完整分析见
[07-稳定性与崩溃分析.md](07-稳定性与崩溃分析.md) 第三节。

**崩溃统计**（`~/Library/Logs/DiagnosticReports`）：

| 进程 | 次数 | 影响 |
|---|---|---|
| `SafariBookmarksSyncAgent` | 27 | 书签同步 |
| `AuthenticationServicesAgent` | 25 | 登录 / 密码 |
| `assistantd` | 24 | Siri |
| `CommCenter` | 22 | 通信 |
| **`Safari`** | **5** | **浏览器打不开** |
| 其他（`dock.extra` / `acountsd` / `sharingd` / `axassetsd`…） | 30+ | — |

**崩溃特征**：

```
EXC_BAD_ACCESS / SIGKILL (Code Signature Invalid) / Invalid Page
栈：libobjc readClass → map_images → _objc_init（死在动态库加载最早期）
```

内核日志能看到具体页面，**地址每次都相同**：

```
CODE SIGNING: cs_invalid_page(0x7ff82742f000): denying page sending SIGKILL
  ... in file ".../dyld/dyld_shared_cache_x86_64h"
```

**原因**：`nullarc` 改写内存页，写脏的页落在 `dyld_shared_cache`（所有系统框架的
共享映射）里，Tahoe 的页级签名校验就把**所有加载到该页的进程**全部 `SIGKILL`。
这也解释了「为什么一堆不相关进程同时崩」—— 它们共享同一页。

**处理**：没有软件层解法。**要 Safari 就回稳定档，要流畅就接受这批应用崩**。

### 2.9 `SafeEjectGPUService` 卡死 100% CPU

```sh
ps -Ao pid,pcpu,command | grep SafeEjectGPU
# 1011  99.2  .../SafeEjectGPUService.xpc/Contents/MacOS/SafeEjectGPUService
```

「安全弹出外接 GPU」菜单栏组件，卡在 `PhxAMDFB` 永不返回的状态查询里。

**`kill -9` 无效**（PID 都不变，不可中断的 D state）。
**影响**：白烧一个逻辑核心。**处理**：无解，除非关 GPU 接管。

详见 [07](07-稳定性与崩溃分析.md) 第四节。

## 三、稳定性风险

### 3.1 WindowServer 偶发崩溃（毛玻璃）

K8 文档记录：2 天 2 次，崩溃栈为

```
CoreDisplay ...
  CA::OGL::BlurState::narrow_blur
  CA::OGL::GaussianBlurFilter::render
  MetalContext::draw
  nvmtl_vk_pipeline_create_rt
  radv_CreateGraphicsPipelines
```

**这是 NVMTL/RADV 创建毛玻璃渲染管线时的驱动段错误，上游未修。**

**缓解**：开启「降低透明度」减少 blur pipeline 创建。

### 3.2 GPU hang

如果 GPU 挂死，WindowServer 会等 fence 直到 watchdog 杀掉它。
`phxboot.sh` 有保护：

- 5 分钟内 2 次 WindowServer 报告 → 重启
- 1 小时内 3 次这样的重启 → `WindowServer` 退回固件帧缓冲

**手动恢复**：

```sh
sudo touch /Users/Shared/gpu/phxboot-off
sudo reboot
```

### 3.3 蓝牙枚举慢

日志显示蓝牙 USB 设备 `busy 0 (7260 ms)`，约 7 秒。

**不影响功能**，但开机后蓝牙比 Wi-Fi 晚可用。
