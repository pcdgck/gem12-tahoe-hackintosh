# 07 — 稳定性与崩溃分析

这台机器有两类稳定性问题，都指向同一个根因：**nullarc 会改写内存页**。

| 类别 | 现象 | 影响 |
|---|---|---|
| **A. 内核 panic** | `pmap` 页表损坏 / 链表损坏 | 只在**关机阶段**发生 |
| **B. 用户态进程被 SIGKILL** | Safari 等几十个系统进程崩 | **运行期**，影响可用性 |

> **结论**：`nullarc`（PhxAccel）在 GPU 接管时改写内存页。
> 写脏的页如果落在 `dyld_shared_cache` 里，Tahoe 的代码签名校验
> 就会把所有加载到该页的进程 `SIGKILL`。
> **「流畅」和「可用」目前无法共存。**

---

## 一、两个档位的取舍

| | 流畅档 | 稳定档 |
|---|---|---|
| 帧缓冲 | `PhxAMDFB` + `NMXAccel` | `IONDRVFramebuffer`（固件） |
| Metal | ✅ Metal 3 | ❌ |
| 界面 | 流畅，拖动 57 fps | 卡顿（`WindowServer` 30~40% CPU） |
| 系统应用 | ❌ **Safari 等批量 SIGKILL** | ✅ 正常 |
| 关机 | ⚠️ 留 `pmap` panic 记录 | ✅ 干净 |

**判断当前档位**：

```sh
ioreg -rc IOFramebuffer -d1 | grep '^+-o'
#   +-o PhxAMDFB        → 流畅档
#   +-o .Display_boot   → 稳定档
```

### 切档

```sh
# 流畅档
sudo touch /Users/Shared/gpu/phxboot-m2
sudo nvram phxfb-boot=1
sudo nvram IONVRAM-FORCESYNCNOW-PROPERTY=phxfb    # 立刻落盘，不等关机
sudo reboot

# 稳定档
sudo rm -f /Users/Shared/gpu/phxboot-m2 /Users/Shared/gpu/phxboot-off
sudo nvram -d phxfb-boot
sudo reboot

# 紧急中止接管
sudo touch /Users/Shared/gpu/phxboot-off && sudo reboot
```

## 二、内核 panic：16 次，全部发生在关机阶段

### 分类

| 类型 | 次数（约） |
|---|---|
| **`pmap` 页表损坏** | 最多 |
| 链表损坏 | 2 |
| page fault / general protection | 4 |
| 网络栈 mbuf | 2 |
| APFS namedstream | 1 |

典型 panic string：

```
panic(cpu 6): Possible memory corruption:
pmap_pv_remove(...): null pv_list, priors: 2 @pmap_internal.h:893
Panicked task: pid 607: siriknowledged
```

**特点**：崩溃进程是随机的（`siriknowledged` / `FamilyControlsAgent` /
`CacheDeleteExtension`…），说明是**系统级内存结构被写坏**，不是应用 bug。

### 关键：panic 的时刻

```
18:17:02  panic（pmap）   ← 紧接着 18:17:05 phxboot 启动
17:54:17  panic（链表）    ← 紧接着 17:54 那次开机
```

**两个 panic 都在「上次运行结束 → 本次启动开始」之间**，即关机/重启阶段。

所以：**运行期相对稳定，但每次关机都留一条 panic 记录**。

```sh
# 查上次关机是否异常（5 = 崩溃/watchdog，0/3 才是正常）
sudo log show --last 24h --predicate 'eventMessage CONTAINS "Previous shutdown cause"' \
  | grep -v 'log run' | tail -5

# 查 panic 列表
sudo ls -lt /Library/Logs/DiagnosticReports/Retired/*.panic | head -5
```

## 三、用户态进程被 SIGKILL（流畅档专属）

### 现象

开启 GPU 接管后，一大批**互不相关**的系统进程反复崩溃：

```
SafariBookmarksSyncAgent      27 次
AuthenticationServicesAgent   25 次
assistantd                    24 次
CommCenter                    22 次
Safari                         5 次   ← 浏览器直接打不开
另有 dock.extra / accountsd / sharingd / axassetsd 等 30+ 次
```

完整清单见 [04-已知问题.md](04-已知问题.md) 2.8。

### 崩溃特征

```
exception  : EXC_BAD_ACCESS
signal     : SIGKILL (Code Signature Invalid)
termination: CODESIGNING / Invalid Page

栈（死在动态库加载最早期，还没进应用代码）:
  libobjc   readClass → map_images → _objc_init
  libSystem libSystem_initializer
```

`SIGKILL` 是**系统强制杀死**，不是应用自身崩溃。

### 机理

内核日志能直接看到具体页面：

```
CODE SIGNING: cs_invalid_page(0x7ff82742f000): p=1193[SafariBookmarksS]
  denying page sending SIGKILL
... rejecting invalid page ... in file ".../dyld/dyld_shared_cache_x86_64h"
```

**地址 `0x7ff82742f000` 每次都一样** —— 是同一个被写脏的共享缓存页。

`dyld_shared_cache` 是所有系统框架的共享内存映射，Tahoe 对它做页级签名校验。
一页被写脏，**所有加载到该页的进程全部 `SIGKILL`** ——
这就是「一堆不相关进程同时崩」的原因。

### 为什么是 nullarc

1. 时间完全对应：稳定档期间没有这类崩溃，开 GPU 后立刻批量崩
2. `PhxAccel` 是内核扩展，接管 GPU 时要建立 GPUVM 页表、映射显存、搬帧缓冲
3. 关机时的 `pmap_pv_remove: null pv_list` 就是「页表被错误改写」的直接证据 ——
   同一个 bug，运行期表现为进程被 SIGKILL，关机期表现为内核 panic

### 缓解方向（未验证）

理论上可以打内核补丁弱化 `cs_invalid_page` 的判罚，把 `SIGKILL` 降级或放行。
但这是修改系统完整性保护，**风险很高，本项目没有尝试**。

## 四、`SafeEjectGPUService` 卡死 100% CPU

```sh
ps -Ao pid,pcpu,command | grep SafeEjectGPU
# 1011  99.2  .../SafeEjectGPUService.xpc/Contents/MacOS/SafeEjectGPUService
```

它是「安全弹出外接 GPU」菜单栏组件，需要轮询 GPU 状态。
`PhxAMDFB` 不是真正的 Apple GPU 驱动，某些状态查询**永不返回**，
于是卡在 ioctl 里忙等。

**杀不掉**（PID 都不变，处于不可中断的 D state）：

```sh
sudo killall SafeEjectGPUService      # 无效
sudo killall -9 SafeEjectGPUService   # 无效
sudo launchctl bootout gui/501/com.apple.SafeEjectGPUAgent   # 无效
```

**影响**：白烧一个逻辑核心。**处理**：无解，除非关 GPU 接管。

## 五、内存已排除

`pmap` 损坏最容易被怀疑成内存条坏了，所以做了实测（`scripts/memtest.c`）：
大块分配 → 四种模式填充 → 逐字节读回校验。

| 规模 | 轮数 | 累计读写 | 结果 |
|---|---|---|---|
| 4 GB | 2 | 32 GB | ✅ 0 错误 |
| 16 GB | 3 | 192 GB | ✅ 0 错误 |
| 32 GB | 1 | 128 GB | ✅ 0 错误 |

累计约 **350 GB 读写，零位翻转** → 内存条无硬错误。

内存配置：`2 × 24 GB DDR5-5600`（Crucial CT24G56C46S5），ECC 关闭。
主板 BIOS 里没有 EXPO/XMP 开关，跑默认频率。

> 软件测试不能替代硬件级 memtest86，但 350 GB 零错误足以排除「内存明显损坏」。

## 六、崩溃后的救援

### 情况 1：正常重启，只留了 panic 记录

不用管。`phxboot` 的 `m2_fail` 机制会检测到并自动降级。

### 情况 2：桌面卡死（鼠标不动）

`phxboot.sh` 注释里写明这种状态「没有回头路，只能重启」。

1. 长按电源 **10 秒**强制关机
2. 开机，立刻连按 `ESC` 或空格进 OpenCore 菜单
3. 选 **Reset NVRAM**（清掉 `phxfb-boot`）
4. 启动后即回到固件帧缓冲

### 情况 3：进不了系统（kext 加载卡死）

OpenCore 菜单 → `Recovery` → 终端：

```sh
diskutil list                       # 找 TYPE 为 EFI EFI 的分区
diskutil mount disk0s1
plutil -replace Kernel.Add.<索引>.Enabled -bool NO /Volumes/EFI/EFI/OC/config.plist
plutil -lint /Volumes/EFI/EFI/OC/config.plist
diskutil unmount /Volumes/EFI && reboot
```

更多恢复流程见 [05-恢复手册.md](05-恢复手册.md)。
