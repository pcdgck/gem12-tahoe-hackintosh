# 07 — 稳定性与崩溃分析

这台机器有两类完全不同的稳定性问题，**必须分开看**：

| 类别 | 现象 | 归因 |
|---|---|---|
| **A. 内核 panic** | 16 次 `pmap` 页表损坏 / 链表损坏 | `nullarc` GPU 接管 |
| **B. 用户态进程被 SIGKILL** | Safari 等几十个系统进程崩 | `nullarc` 改写 `dyld_shared_cache` 页面 |

两者都指向同一个根因：**nullarc 会破坏内存页**。

> **结论先行**：`nullarc`（PhxAccel）在 GPU 接管时会改写内存页。
> 这既会让内核在关机阶段 panic，也会让 Tahoe 的代码签名检查
> 大批 `SIGKILL` 系统进程（Safari 直接打不开）。
> **「流畅」和「可用」目前无法共存。**

---

## 一、两个档位的真实代价

### 流畅档（GPU 接管开启）

```
帧缓冲:        PhxAMDFB
Metal:         3
GPU 合成:      iop_ok 持续增长
WindowServer:  0.6% ~ 13% CPU
界面:          流畅，拖动 57 fps
```

**代价（全部是 nullarc 造成的）**：

| 问题 | 严重性 |
|---|---|
| 每次关机/重启 `pmap` panic | 中（不影响运行） |
| **Safari 及大批系统进程被 SIGKILL** | **高（应用直接不可用）** |
| `SafeEjectGPUService` 100% CPU | 中（白烧一个核心） |
| 部分进程反复崩溃 | 高 |

### 稳定档（GPU 接管关闭）

```
帧缓冲:        IONDRVFramebuffer（固件帧缓冲）
GPU 合成:      无
WindowServer:  30~40% CPU（软件合成）
界面:          明显卡顿
```

**代价**：界面卡。
**收益**：零 panic、零进程崩溃、关机干净。

### 怎么判断当前在哪个档位

```sh
ioreg -rc IOFramebuffer -d1 | grep '^+-o'
#   +-o PhxAMDFB        → 流畅档
#   +-o .Display_boot   → 稳定档
```

## 二、内核 panic：16 次，但**都发生在关机阶段**

### 完整分类

采集时段 2026-11-23 18:14 ~ 11-24 18:17。

| 类型 | 次数 | 说明 |
|---|---|---|
| **`pmap` 页表损坏** | **最多** | `pmap_pv_remove: null pv_list` |
| 链表损坏 | 2 | `corrupt list around element 0x...` |
| page fault / general protection | 4 | trap 13 / trap 14 |
| 网络栈 mbuf | 2 | `M_PKTHDR`（装 AppleIGC 期间） |
| APFS namedstream | 1 | — |

### 两个典型 panic string

`pmap` 类（最多）：

```
panic(cpu 6): Possible memory corruption:
pmap_pv_remove(0xffffffa3bd48f800, 0x7ff94bc06000, 0x680, ...):
null pv_list, priors: 2 @pmap_internal.h:893
Panicked task: pid 607: siriknowledged
```

链表损坏类：

```
panic(cpu 0): corrupt list around element 0xffffff90c7f7aef8
  at 0xffffff800cd603d2
```

**共同点**：崩溃进程是**随机的**（`siriknowledged`、`FamilyControlsAgent`、
`CacheDeleteExtension`、`calaccessd`……），不是某个应用的 bug，
而是**系统级内存结构被写坏**。

### 关键观察：panic 的时刻

对照 `phxboot` 日志后发现一个关键规律：

```
18:17:02  panic（pmap）      ← 紧接着 18:17:05 phxboot 启动
17:54:17  panic（链表损坏）   ← 紧接着 17:54 那次开机
```

**两个 panic 都发生在「上一次运行结束 → 本次启动开始」之间，
也就是关机/重启阶段，而不是运行中。**

这解释了为什么「系统用起来感觉没事，但 `Previous shutdown cause` 一直是 5」：

```sh
sudo log show --last 24h --predicate 'eventMessage CONTAINS "Previous shutdown cause"' \
  | grep -v 'log run' | tail -5
#   Previous shutdown cause: 5     ← 5 = 崩溃/watchdog，0/3 才是正常
```

**含义**：运行期间相对稳定，但每次关机都留一条 panic 记录。
数据安全风险不算高，但绝不算"干净"。

## 三、用户态进程被 SIGKILL：GPU 接管的直接后果

### 现象

开启 GPU 接管后，大量系统进程反复崩溃（统计自 `~/Library/Logs/DiagnosticReports`）：

| 进程 | 崩溃次数 | 影响 |
|---|---|---|
| `SafariBookmarksSyncAgent` | **27** | 书签同步 |
| `AuthenticationServicesAgent` | **25** | 登录/密码验证 |
| `assistantd` | **24** | Siri |
| `CommCenter` | **22** | 通信/电话 |
| `axassetsd` | 7 | 辅助功能资源 |
| `sharingd` | 6 | 共享/AirDrop |
| `com.apple.dock.extra` | 6 | 程序坞扩展 |
| `acountsd` | 5 | 账户 |
| **`Safari`** | **5** | **浏览器打不开** |
| `siriactionsd` | 4 | Siri 动作 |

### Safari 的崩溃报告

```
exception  : EXC_BAD_ACCESS
signal     : SIGKILL (Code Signature Invalid)
termination: CODESIGNING / Invalid Page

触发栈:
  libobjc.A.dylib   readClass(objc_class*, bool, bool)
  libobjc.A.dylib   map_images_nolock
  libobjc.A.dylib   map_images
  dyld              ...setObjCNotifiers...
  libSystem.dylib   libSystem_initializer
  dyld              ...findAndRunAllInitializers...
```

**它死在动态库加载的最早期**（objc 类映射阶段），还没跑 Safari 自己的代码。
`SIGKILL` 是**系统强制杀的**，不是应用自己崩。

### 机理：`dyld_shared_cache` 的页面被改写

内核日志能直接看到：

```
CODE SIGNING: cs_invalid_page(0x7ff82742f000): p=1193[SafariBookmarksS]
  final status 0x23016a00, denying page sending SIGKILL

CODE SIGNING: process 1193[SafariBookmarksS]: rejecting invalid page
  at address 0x7ff82742f000 from offset 0x23aef000 in file
  "/System/Volumes/Preboot/Cryptexes/OS/System/Library/dyld/dyld_shared_cache_x86_64h"
```

注意 **地址 `0x7ff82742f000` 每次都一样** —— 那是同一个被写过的页面。

`dyld_shared_cache` 是所有系统框架的共享内存映射，Tahoe 会对它做页级签名校验。
只要有一页被写脏，**所有加载到这一页的进程都会被 `SIGKILL`** ——
这正好解释了为什么是"一堆不相关的系统进程同时崩"。

### 为什么怀疑是 nullarc

1. **时间完全对应**：稳定档期间（17:54–18:17）没有这类崩溃，
   18:17 开 GPU 后立刻开始批量崩。
2. **它能写内存**：`PhxAccel` 是内核扩展，在接管 GPU 时要建立 GPUVM 页表、
   映射显存、搬运帧缓冲 —— 有充分的机会写坏不该写的页面。
3. **同类问题的另一面**：关机时的 `pmap_pv_remove: null pv_list` 就是
   "页表被错误改写"的直接证据。同一个 bug，在运行期表现为进程被 SIGKILL，
   在关机型表现为内核 panic。

### 一个可能的缓解方向（未验证）

Tahoe 的这项检查是 `codeSigningMonitor`。崩溃报告里显示它是 `0`（已关闭），
`csr-active-config = 7F080000`（SIP 全关）也没能绕过。

理论上可以从 boot-args 或内核补丁层面弱化 `cs_invalid_page` 的判罚
（把 `SIGKILL` 降级为 `cs_require_lv` 或直接放行），
但**这属于修改系统完整性保护，风险很高，本项目没有尝试**。

更务实的做法：**回稳定档**，或者等 nullarc 修掉写内存的问题。

## 四、`SafeEjectGPUService` 卡死 100% CPU

### 现象

开启 GPU 接管后：

```sh
ps -Ao pid,pcpu,command | grep SafeEjectGPU
# 1011  99.2  /System/Library/CoreServices/Menu Extras/SafeEjectGPUExtra.menu/...
#               XPCServices/SafeEjectGPUService.xpc/Contents/MacOS/SafeEjectGPUService
```

持续 **99~100% CPU**，白白烧掉一个核心。

### 这是什么

`SafeEjectGPU` 是 macOS 的「安全弹出外接 GPU」菜单栏组件。
它需要轮询 GPU 状态来判断"能不能安全断开"。

`PhxAMDFB` 不是真正的 Apple GPU 驱动，它提供的某些状态查询
**永远不返回或永远返回异常** —— 于是这个 XPC service 卡在
某个 ioctl 里忙等。

### 为什么杀不掉

```sh
sudo killall SafeEjectGPUService      # 无效
sudo killall -9 SafeEjectGPUService   # 无效，PID 都不变
sudo launchctl bootout gui/501/com.apple.SafeEjectGPUAgent   # 无效
```

**`kill -9` 之后 PID 不变** —— 说明进程卡在内核调用里，
处于不可中断的睡眠状态（D state），信号无法投递。
只能等它调用的那个内核函数返回，而那永远不会发生。

**这是 nullarc 的另一个"不返回"缺陷**，不是配置问题。

### 影响与处理

- 影响：一个核心 100% 占用（48 GB 机器上有 16 个逻辑核心，占比 6%）
- 处理：目前**无解**，除非关闭 GPU 接管
- 想验证是不是它：`ps -Ao pcpu,command | sort -rn | head -3`

## 五、内存已排除（不是内存条的锅）

`pmap` 损坏最容易被怀疑成「内存条坏了」，所以做了实测。

### 测试方法

自写 C 程序（`scripts/memtest.c`）：

1. `malloc` 大块内存 + `memset` 触碰所有页（强制物理分配）
2. 按 8 字节写入固定模式（`0xA5` / `0x5A` / `0xFF` / `0x00`）
3. **逐字节读回比对**，任何一位不一致都计错并打印首个错误偏移

```sh
clang -O2 -o memtest memtest.c
./memtest 16 3     # 每块 16 GB，跑 3 轮
```

### 结果

| 规模 | 轮数 | 累计读写 | 结果 |
|---|---|---|---|
| 4 GB | 2 | 32 GB | ✅ 0 错误 |
| 16 GB | 3 | 192 GB | ✅ 0 错误 |
| **32 GB** | 1 | 128 GB | ✅ 0 错误 |

四种模式交替，累计约 **350 GB 读写，零位翻转**。

**内存条本身没有可检测的硬错误。**

### 内存配置

```
2 × 24 GB DDR5-5600
Part Number: CT24G56C46S5.M8B1   (Crucial 24GB DDR5-5600 SODIMM)
ECC: Disabled
```

> 24 GB 是「非二进制容量」，双通道颗粒排布特殊，理论上是稳定性风险点。
> 但实测零错误，不是当前问题源。
> 这块主板 BIOS 里**没有 EXPO / XMP 开关**，内存跑默认频率。

> 软件测试不能替代硬件级 memtest86（后者禁用缓存、做更激进的 pattern），
> 但 350 GB 零错误已足以排除「内存明显损坏」。

## 七、怎么切档位

### 切到流畅档（有上面全部副作用）

```sh
sudo touch /Users/Shared/gpu/phxboot-m2
sudo nvram phxfb-boot=1
sudo nvram IONVRAM-FORCESYNCNOW-PROPERTY=phxfb    # 立刻落盘，不等关机
sudo reboot
```

> `phxboot` 的 M2 流程本来需要两次启动（第一次 arm、第二次接管），
> 直接写 `nvram phxfb-boot=1` 可以省掉一次重启。

### 切到稳定档（推荐，除非必须要流畅）

```sh
sudo rm -f /Users/Shared/gpu/phxboot-m2
sudo rm -f /Users/Shared/gpu/phxboot-off
sudo nvram -d phxfb-boot
sudo reboot
```

### 紧急中止 GPU 接管

```sh
sudo touch /Users/Shared/gpu/phxboot-off
sudo reboot
```

## 八、panic / 卡死后的救援

### 情况 1：正常重启，只是留了 panic 记录

不用管，`phxboot` 的 `m2_fail` 机制会检测到并自动降级。

### 情况 2：桌面卡死（鼠标不动）

`phxboot.sh` 注释里写明这种状态「没有回头路，只能重启」。

1. 长按电源 **10 秒**强制关机
2. 开机，立刻连按 `ESC` 或空格进 OpenCore 菜单
3. 选 **Reset NVRAM**（清掉 `phxfb-boot`，阻止 GPU 再接管）
4. 启动后即回到固件帧缓冲

### 情况 3：进不了系统（kext 加载卡死）

如果之后又折腾了别的 kext 导致无法启动：

1. OpenCore 菜单 → `Recovery`
2. 菜单栏 `实用工具 → 终端`
3. 挂载 EFI 改配置：

```sh
diskutil list                       # 找 EFI 分区（TYPE 是 EFI EFI）
diskutil mount disk0s1
# 关掉对应的 kext（改 Enabled 为 false）
plutil -replace Kernel.Add.<索引>.Enabled -bool NO /Volumes/EFI/EFI/OC/config.plist
plutil -lint /Volumes/EFI/EFI/OC/config.plist
diskutil unmount /Volumes/EFI
reboot
```
