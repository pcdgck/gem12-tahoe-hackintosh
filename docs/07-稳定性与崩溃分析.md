# 07 — 稳定性与崩溃分析

这台机器会偶发内核 panic。这一章是**完整的事后分析**：
12 个 panic 的逐个分类、如何排除内存、最终定位到 `nullarc`（PhxAccel），
以及「稳定」和「流畅」为什么只能二选一。

> **结论先行**：`nullarc` 的 GPU 接管（`PhxAMDFB`）
> 是 `pmap` 页表损坏类 panic 的最可能来源。
> 关掉 GPU 接管后系统可用（但界面无合成，比较卡）。

---

### 分布

| 类型 | 次数 |
|---|---|
| **pmap 页表损坏** | **5** |
| page fault / general protection | 4 |
| 网络栈 mbuf | 2 |
| APFS namedstream | 1 |

**关键观察 1**：`pmap` 崩溃在 **11-23 18:14** 就出现了，
而 `AppleIGC` 是 11-24 04:2x 才装上的。**时间上完全对不上。**

**关键观察 2**：崩溃的进程是**随机的** —— `FamilyControlsAgent`、
`CacheDeleteExtension`、`calaccessd`、`amsondevicestoraged`……
不是某个应用的 bug，而是**系统级内存结构被写坏**。

### 两个典型的 panic string

`pmap` 类（占最多）：

```
panic(cpu 13): Possible memory corruption:
pmap_pv_remove(0xffffff9040ad2b80, 0x7f8d19007000, 0x800000, ...):
null pv_list, priors: 2 @pmap_internal.h:893
Panicked task: pid 571: FamilyControlsAgent
```

`null pv_list` = 页表的物理→虚拟反向映射链表是空的，
说明**页表项本身被错误改写或释放**。

网络栈类（只有 2 次，全部在装 AppleIGC 之后）：

```
panic(cpu 0): assertion failed: m->m_flags & M_PKTHDR,
file: bsd/kern/uipc_mbuf.c, line: 4839 @uipc_socket.c:8286
Backtrace: _dlil_create_input_thread + 0x2257 / +0x2596
Panicked task: pid 0: kernel_task
```

## 二、先排除内存：内存压力测试

`pmap` 损坏最容易被怀疑成「内存条坏了」。所以先做实测。

### 测试方法

自写 C 程序（`scripts/memtest.c`），逻辑：

1. `malloc` 大块内存并用 `memset` 触碰所有页（强制物理分配）
2. 按 8 字节写入固定模式（`0xA5` / `0x5A` / `0xFF` / `0x00` 四种）
3. **逐字节读回比对**，任何一位不一致都计错并打印首个错误偏移

比 `numpy` 方案更可靠：纯 C、无额外依赖、直接看位翻转。

```sh
clang -O2 -o memtest memtest.c
./memtest 16 3     # 每块 16 GB，跑 3 轮
```

### 测试结果

| 规模 | 轮数 | 累计读写 | 结果 |
|---|---|---|---|
| 4 GB | 2 | 32 GB | ✅ 0 错误 |
| 16 GB | 3 | 192 GB | ✅ 0 错误 |
| **32 GB** | 1 | 128 GB | ✅ 0 错误 |

四种模式交替，累计约 **350 GB 读写，零位翻转**。

**结论：内存条本身没有可检测的硬错误。** `pmap` 损坏不是内存颗粒导致的。

> 说明：软件测试不能替代硬件级 memtest86（后者会禁用缓存、做更激进的 pattern），
> 但 350 GB 零错误已经足以排除「内存明显损坏」这个方向。

### 内存配置

```
2 × 24 GB DDR5-5600
Part Number: CT24G56C46S5.M8B1   (Crucial 24GB DDR5-5600 SODIMM)
ECC: Disabled
```

> 24 GB 是「非二进制容量」（不是 16/32 这种 2 的幂），
> 双通道时颗粒排布比较特殊，理论上是稳定性风险点。
> 但实测没有错误，所以不是当前的问题源。
> 这块主板的 BIOS 里**没有 EXPO / XMP 开关**，内存跑默认频率。

## 三、定位到 `nullarc`（PhxAccel）

排除内存后，嫌疑集中在 `nullarc`：

| 证据 | 说明 |
|---|---|
| `pmap_pv_remove: null pv_list` | **页表结构被破坏** |
| 崩溃进程随机 | 系统级内存被写坏，不是应用 bug |
| 11-23 18:14 就有 | 那时 AppleIGC 还不存在，但 GPU 早已在跑 |
| `nullarc` 操作 **GPUVM 页表** | 有权限也可能影响 CPU 侧 `pmap` |
| upstream 自己的警告 | 「alpha 阶段，**可能导致内核 panic、数据损坏**」 |

`PhxAMDFB` 接管面板时要做的事：

1. 从 BIOS 固件手里夺过 scanout（扫描输出）
2. 建立 GPU 虚拟内存（GPUVM）页表
3. 映射显存、映射帧缓冲
4. 把面板从固件 GOP 切到 PhxAMDFB

**第 2、3 步涉及大量页表操作。** 如果 GPUVM 的映射范围算错、
或者在接管瞬间和 CPU 侧的 `pmap` 竞争同一段物理页，
就会出现 `null pv_list` 这种「页表被删了两次 / 删错了」的损坏。

**验证方法就是关掉它**：

```sh
# 恢复 GPU 接管（风险：可能再 panic）
sudo touch /Users/Shared/gpu/phxboot-m2 && sudo reboot

# 关闭 GPU 接管（推荐，稳定优先）
sudo rm -f /Users/Shared/gpu/phxboot-m2 /Users/Shared/gpu/phxboot-off
sudo nvram -d phxfb-boot
sudo reboot
```

关闭后 `phxboot` 日志会显示 `PhxAMDFB on the panel: 0`，
帧缓冲退回 `IONDRVFramebuffer`（固件帧缓冲）。

## 四、稳定 vs 流畅：只能二选一

这是本项目最核心的取舍。

| 配置 | GPU 合成 | 界面流畅度 | 稳定性 |
|---|---|---|---|
| **GPU 接管开启** | ✅ `PhxAMDFB` + `NMXAccel` | ✅ Metal 3，拖动 57 fps | ❌ 偶发 `pmap` panic |
| **GPU 接管关闭** | ❌ `IONDRVFramebuffer` | ⚠️ CPU 合成，明显卡顿 | ✅ 可长期运行 |

### 判断是否在"稳定档"

```sh
# 帧缓冲是谁
ioreg -rc IOFramebuffer -d1 | grep -E '^\+-o'
#   PhxAMDFB            → GPU 接管中（流畅档，有 panic 风险）
#   .Display_boot / IONDRVFramebuffer → 固件帧缓冲（稳定档）

# GPU 合成帧计数（为 0 或不存在 = 没接管）
sysctl -n debug.nvaccel_iop_ok
```

### 怎么观察稳定性

```sh
# 最近的 panic 列表
sudo ls -lt /Library/Logs/DiagnosticReports/Retired/*.panic | head -5

# 上次关机是不是异常（5 = 崩溃/watchdog，0/3 = 正常）
sudo log show --last 24h --predicate 'eventMessage CONTAINS "Previous shutdown cause"' \
  | grep -v 'log run' | tail -5
```

**建议**：切到稳定档后连续跑 24-48 小时，
如果 `cause: 5` 不再出现，就可以确认 panic 来自 GPU 接管。

## 五、复现与救援

### panic 之后的连锁反应

panic 是**非正常关机**，会留下 `/var/db/phxboot.pending` 标记。
下次启动时 `phxboot` 的处理逻辑是：

```
检测到 pending
  → 创建 phxboot-off（关闭 GPU 接管）
  → 清除 NVRAM 里的 phxfb-boot
  → 如果 PhxAMDFB 已经接管了面板 → 立即重启（让它别接管）
```

如果这个流程成功，第二次启动就回到固件帧缓冲，**能正常显示**。

### 最坏情况：桌面卡死（鼠标不动）

如果看到桌面但完全无响应，说明 `PhxAMDFB` 接管了面板
但 WindowServer 在接管完成前打开了面板 ——
`phxboot.sh` 自己注释里写着「没有回头路，只能重启」。

> 本机在 2026-11-24 04:45 就撞上过这个状态，
> `phxboot` 在 90 秒后判定 `M2 failed (no WindowServer)` 并强制重启。

**救援步骤**：

1. 长按电源 **10 秒**强制关机
2. 开机，立刻连按 `ESC` 或空格进 OpenCore 菜单
3. 选 **Reset NVRAM**（清掉 `phxfb-boot`，阻止 GPU 再接管）
4. 启动后即回到固件帧缓冲

### 三个"档位"开关速查

| 想做的事 | 操作 |
|---|---|
| 临时关闭 GPU 接管 | `sudo touch /Users/Shared/gpu/phxboot-off && sudo reboot` |
| 恢复 GPU 接管 | `sudo rm -f /Users/Shared/gpu/phxboot-m2.off; sudo touch /Users/Shared/gpu/phxboot-m2 && sudo reboot` |
| 清掉残留状态 | `sudo rm -f /var/db/phxboot.pending /Users/Shared/gpu/phxboot-off; sudo nvram -d phxfb-boot` |
